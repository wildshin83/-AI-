# 프로젝트 일정 승인 및 사용자 권한·계정 복구 설계

- 작성일: 2026-10-16
- 상태: 2026-10-16 사용자 서면 설계 승인 완료. 구현 계획 검토 단계.
- 확인 주체: CS사업부 기술팀 책임자 신형섭 및 서비스 관리자
- 적용 범위: 로그인 계정 관리, 프로젝트 일정 표시·변경·승인, 관련 이력과 패키지 호환
- 단계: 기존 MVP 후속 고도화

## 1. 목적과 확정 요구

고객 납기일·입고 일정·FOB 일정을 구분하고 날짜를 눌러 확인·수정한다. 1단계 사용자의 변경은 승인 후 반영하며, 2단계 사용자와 관리자는 직접 수정하고 승인 요청도 처리한다. 관리자는 가입 승인 때 단계 권한을 선택하고 기존 사용자 목록에서도 권한을 선택해 행별 저장할 수 있다.

추가 요구인 계정 분실 대응은 관리자 이름 검색을 통한 아이디 확인과 임시 비밀번호 재발급으로 제공한다. 기존 비밀번호는 해시이므로 조회하거나 복호화하지 않는다. 임시 비밀번호는 발급 응답에서만 한 번 표시하고 사용자가 다음 로그인 때 변경한다.

기존 고객 납기일, 관리자 지위, 프로젝트 자료와 업무 이력을 보존한다. 승인 알림과 요청 처리는 앱 내부 화면으로 제공한다. 이메일 발송을 추가하지 않는다.

## 2. 접근 방식

선택안은 기존 계정 모델에 사용자 단계 필드를 추가하고 일정 변경 전용 모델·서비스를 두는 방식이다. 기존 가입 승인, 인증 미들웨어와 공통 감사 서비스를 재사용한다. 범용 결재 엔진 방식은 현재 요구보다 범위가 크고 여러 업무의 승인 규칙을 미리 일반화해야 하므로 채택하지 않는다.

화면은 서비스에 명시적 사용자와 입력값을 전달한다. 권한 판정과 일정 변경은 서비스에서 처리하고 요청 파라미터나 화면에 표시된 버튼만으로 권한을 신뢰하지 않는다.

## 3. 사용자 권한

| 동작 | 1단계 | 2단계 | 관리자 |
|---|---|---|---|
| 프로젝트 일정 조회 | 가능 | 가능 | 가능 |
| 기존 일정 직접 변경 | 불가 | 가능 | 가능 |
| 일정 변경 요청 | 가능 | 직접 수정 제공 | 직접 수정 제공 |
| 일정 요청 승인·반려 | 불가 | 가능 | 가능 |
| 계정 승인·생성·단계 변경 | 불가 | 불가 | 가능 |
| 다른 사용자 아이디 확인·비밀번호 재발급 | 불가 | 불가 | 가능 |

`AuthUser.permission_level`을 정수 1 또는 2로 추가한다. 기존 `is_admin`이 관리자 지위의 기준이며 단계 선택으로 관리자 승격을 허용하지 않는다. 기존 일반 계정은 1단계로 채운다. 관리자 계정은 기존 지위를 유지하고 단계 필드를 2로 정규화한다.

가입 승인 폼과 관리자 수동 계정 등록 폼은 1단계·2단계 선택을 제공하며 기본값은 1단계다. 기존 계정 Excel 양식은 유지하고 일괄 생성 계정은 1단계로 등록한다. 필요하면 관리자 목록에서 개별 변경한다. 공개 가입 신청자가 승인 권한을 지정할 수는 없다.

기존 사용자 목록의 권한 열에서 일반 계정은 드롭다운과 해당 행 전용 저장 버튼을 표시한다. 관리자 행은 관리자임을 표시하며 이 드롭다운으로 관리자 지위를 변경하지 않는다. 저장은 계정 ID를 기준으로 수행하며 성공·실패를 해당 계정을 식별할 수 있는 메시지로 알린다. 화면은 관리자 이름 검색으로 사용자 이름과 이메일 아이디를 찾을 수 있게 한다.

권한 저장은 최신 계정을 DB에서 다시 확인하고 `auth_version`을 증가시켜 이전 세션을 무효화한다. 대상 사용자는 재로그인 후 새 권한을 사용한다. 일정 변경·승인과 계정 관리의 쓰기 요청에서도 최신 활성 여부와 권한·세션 버전을 DB에서 확인한다. 기존 10초 인증 캐시를 권한 변경 직후의 쓰기 허용 근거로 사용하지 않는다.

## 4. 일정 데이터와 신규 등록

| 업무 명칭 | 저장 필드 | 기존 데이터 처리 |
|---|---|---|
| 고객 납기일 | `projects.target_delivery_date` | 값과 필드명을 유지하고 화면 명칭 변경 |
| 입고 일정 | `projects.incoming_date` | nullable Date 추가, 초기값 없음 |
| FOB 일정 | `projects.fob_date` | nullable Date 추가, 초기값 없음 |

세 값은 시간대 없는 달력 날짜다. 미입력은 NULL이며 화면에서는 미입력으로 표시한다. 순서가 다른 업무 일정도 가능하므로 날짜 간 선후를 자동으로 강제하지 않는다. 유효하지 않은 달력 날짜는 저장하지 않고 해당 필드 오류를 표시한다.

신규 프로젝트 등록 시 모든 로그인 사용자가 최초 세 날짜를 선택 입력할 수 있다. 신규 프로젝트 생성과 기존 일정 변경을 구분하며, 생성 이후 1단계 사용자의 일정 변경은 반드시 요청 경로를 따른다. 변경 사유는 직접 수정과 요청 모두 필수이며 공백 제거 후 1~2,000자로 제한한다. 실제 날짜 변경이 없는 제출은 안내하고 저장하지 않는다.

프로젝트에 `schedule_version` 정수 필드를 추가하고 기본값은 1로 둔다. 일정 변경 때만 1씩 증가시켜 변경 후 원래 날짜로 돌아온 경우에도 오래된 요청이나 편집 화면을 감지한다.

## 5. 프로젝트 상세 화면

기존 진행 단계 표시를 진행 상태 아래에 유지한다. 데스크탑은 진행 상태, 세 일정을 묶은 일정 영역, 보관 상태를 같은 요약 카드에 배치하고 일관된 간격을 적용한다. 일정 영역 안의 고객 납기일·입고 일정·FOB 일정은 같은 너비와 간격으로 정렬한다. 모바일은 진행 상태와 단계 표시 바로 다음에 일정 영역, 보관 상태가 이어지도록 배치한다.

날짜와 미입력 표시는 모두 클릭 가능한 링크로 제공한다. 어느 날짜를 눌러도 세 날짜와 현재 변경 이력을 보는 공통 일정 화면으로 이동하고, 선택한 날짜 입력에 초점을 준다. 별도 일정 화면은 작은 화면과 키보드에서도 사용할 수 있도록 구현한다. 큰 모달·클라이언트 프레임워크 추가는 필요하지 않다.

1단계 화면의 제출 버튼은 승인 요청, 2단계·관리자의 버튼은 일정 저장이다. 대기 요청이 있으면 프로젝트 일정 화면에 신청자·기존/제안 날짜·사유·상태를 표시한다. 프로젝트 목록의 기존 납기 열은 고객 납기일로 이름을 바꾸고 정렬 기준은 기존 날짜 필드를 사용한다.

## 6. 일정 변경 요청과 승인

`ScheduleChangeRequest` 모델은 프로젝트 ID, 신청자 계정 ID, 신청 당시 이름, 요청 당시 일정 버전, 기존 세 날짜와 제안 세 날짜, 신청 사유, 처리 상태, 신청 시각, 검토자 계정 ID·이름, 검토 시각, 검토 의견을 가진다. 날짜는 명시적 Date 필드로 저장하고 상태는 pending/approved/rejected/conflicted로 제한한다. 감사 기록은 요청 모델과 함께 사용한다.

한 프로젝트에는 대기 요청을 하나만 허용한다. 프로젝트 행 잠금 아래에서 대기 요청 존재를 확인하고 생성해 동시 제출도 직렬화한다. 요청자는 대기 중 추가 제출을 시도하면 기존 요청으로 안내받는다. 변경 내용을 다시 제출하려면 검토자가 기존 요청을 반려하고 새 요청을 제출한다. 이번 범위에는 대기 요청 편집·취소를 추가하지 않는다.

승인은 서버에서 최신 검토자의 권한을 확인한 다음 프로젝트 행과 요청 행을 일관된 순서로 잠그고 처리한다. 요청이 pending이고 프로젝트 일정 버전이 요청 시점과 같을 때만 세 날짜, 일정 버전 증가, 요청 승인, 감사 기록을 같은 트랜잭션으로 저장한다. 중복 클릭이나 두 검토자의 동시 승인은 한 번만 반영한다.

현재 일정 버전이 달라졌으면 해당 요청을 conflicted로 마감하고 새 요청이 필요하다고 안내한다. 자동 덮어쓰기나 자동 병합을 하지 않는다. 2단계·관리자가 직접 저장할 때도 화면에서 받은 일정 버전과 DB 버전을 비교한다. 불일치하면 입력을 보존하고 최신 날짜를 다시 확인하도록 안내한다.

직접 수정 시 대기 요청이 있으면 기존 요청을 conflicted로 마감하고, 요청자가 재요청해야 한다는 안내를 표시한다. 직접 변경과 기존 요청 마감도 같은 트랜잭션에 포함한다. 반려 시 기존 일정은 유지하며 반려 사유 1~2,000자를 요구한다. 승인 의견은 선택 입력 2,000자 이하다.

## 7. 요청함과 조회 범위

로그인 메뉴에 일정 요청함을 추가한다. 1단계 사용자는 본인의 요청과 처리 결과를 보고, 2단계·관리자는 전체 대기 요청과 처리 이력을 보고 승인·반려할 수 있다. 목록은 상태 필터와 페이지 구분을 제공하고 기본적으로 페이지당 30건을 조회한다. 읽음 추적이나 이메일 전송은 포함하지 않는다.

프로젝트의 현재 일정은 기존 공유 업무 데이터 범위대로 모든 로그인 사용자가 조회한다. 프로젝트 일정 화면은 해당 프로젝트의 변경 이력도 제공한다. 요청 상세 페이지에서의 신청자 전용 조회와 검토자 전체 조회는 서버에서 제한한다. 2단계 사용자가 계정 관리 URL을 요청하면 기존 관리자 전용 규칙대로 거절한다.

## 8. 관리자 계정 분실 대응

관리자 사용자 목록에서 이름·이메일로 아이디를 검색하고, 일반 계정 행의 비밀번호 재발급 동작으로 새 임시 비밀번호를 발급한다. 재발급 폼에는 대상 이름·아이디와 대상 사용자의 기존 로그인 세션이 종료된다는 영향을 표시하고 별도 제출 버튼을 둔다.

임시 비밀번호는 서버의 암호학적 난수로 20자 이상 생성하고 현재 PBKDF2 해시 함수로만 저장한다. 응답에서 관리자에게 한 번 표시해 직접 전달할 수 있도록 한다. 새로고침 후에는 다시 조회하지 못한다. 평문 비밀번호를 DB·감사 기록·URL·로그에 남기지 않고, 해당 응답에는 `Cache-Control: no-store`를 적용한다. 응답 유실 시 다시 발급한다.

재발급 시 `must_change_password=True`, `auth_version` 증가, 로그인 실패 수·잠금 상태 초기화를 같은 트랜잭션에 적용한다. 비활성 계정은 자동 활성화하지 않는다. 일반 계정의 권한도 그대로 유지한다. 감사에는 실행 관리자·대상 계정 ID·시각만 기록한다. 이번 기능의 재발급 대상은 일반 사용자이며 관리자 계정 자체의 분실 복구는 기존 운영 절차를 유지한다.

### 퇴사자 등 계정 비활성화

기존 사용자 목록의 일반 계정 상태 열에 활성·비활성 드롭다운과 상태 전용 행별 저장 버튼을 둔다. 권한 열의 단계 저장과 별개로 선택한 상태를 저장한다. 관리자는 비활성 계정을 다시 활성화할 수 있으며 관리자 계정 자체의 비활성화는 이 화면에서 제공하지 않는다.

상태 변경은 `is_active`와 `auth_version` 증가 및 감사 기록을 같은 트랜잭션에 저장한다. 비활성화는 계정·기존 업무 기록·신청 이력을 삭제하지 않는다. 재활성화해도 이전 세션은 다시 유효해지지 않으며 새로 로그인해야 한다. 실제 상태나 권한이 바뀌지 않은 저장은 세션을 종료하지 않는다.

비활성 계정이 올바른 이메일과 비밀번호로 로그인하면 로그인 화면에 정확히 **권한이 만료되어 접속할 수 없습니다.** 를 표시한다. 잘못된 아이디·비밀번호에는 기존 로그인 실패 안내를 유지한다. 비활성 상태 안내로 비밀번호 검증을 생략하지 않는다. 로그인된 사용자가 비활성화되면 다음 보호된 요청에서 세션 쿠키를 제거하고 로그인 화면으로 이동하며 같은 안내를 표시한다. 안내 전달에는 비밀정보 없는 고정 상태 코드만 사용하고 로그인 폼에서 고정 문구로 변환한다.

활성 여부와 세션 버전은 보호된 요청마다 DB에서 확인한다. 화면용 이름·단계 캐시를 쓰더라도 캐시에 남은 활성 상태로 접근을 허용하지 않는다. Vercel의 여러 인스턴스에서도 비활성화·세션 무효화가 다음 요청부터 적용되어야 한다. DB에서 확인할 수 없으면 인증된 업무 접근을 허용하지 않는다.

## 9. 감사 이력과 공통 규칙

공통 `record_audit`를 사용해 일정 요청·승인·반려·충돌·직접 수정, 가입 승인 권한, 기존 사용자 단계 변경, 계정 활성·비활성 변경, 비밀번호 재발급을 남긴다. 일정 기록에는 변경 전후 날짜, 버전, 사유, 요청 ID, 실행자 계정 ID·표시명을 포함한다. 비밀번호 평문·해시·세션 토큰은 기록하지 않는다.

중요 상태 갱신과 감사는 같은 DB 트랜잭션을 사용한다. 중간 실패 시 전체 롤백한다. 화면에는 권한 부족, 이미 처리된 요청, 다른 사용자에 의한 일정 변경, 유효하지 않은 날짜를 구분해 한국어로 안내한다. 기존 로그인 게이트와 요청 출처 검증을 유지한다.

## 10. 마이그레이션과 패키지 호환

현 Alembic 최신 리비전 `20261016_0011` 다음에 사용자 단계, 두 날짜, 일정 버전, 요청 테이블·외래키·조회 인덱스·제약을 추가한다. PostgreSQL을 운영 기준으로 삼고 SQLite 개발 환경도 마이그레이션 가능하도록 한다. 외래키로 연결된 계정이나 프로젝트를 이 기능에서 삭제하지 않는다.

프로젝트 패키지의 v2 형식을 유지하며 프로젝트 메타데이터에 두 날짜를 선택 필드로 추가한다. 이전 v2에 필드가 없으면 NULL로 읽는다. 기존 고객 납기일 키는 유지한다. 요청·승인·계정 권한·세션 및 일정 버전은 패키지로 가져오지 않는다. 새로 가져온 프로젝트의 일정 버전은 1이다. 기존 프로젝트 번호의 자동 병합·덮어쓰기 금지는 유지한다.

운영 적용은 DB 백업 확인, 마이그레이션 적용, 앱 배포 순서로 수행한다. 컬럼·테이블을 추가하는 변경이므로 기존 버전 앱과 읽기 호환을 유지한다. 되돌릴 때는 앱을 먼저 되돌리고 새 일정·요청 데이터가 생긴 뒤 DB downgrade로 데이터를 삭제하지 않는다. 스키마 마이그레이션은 기존에 승인된 운영 DB 범위에서 수행하고 비밀정보는 출력하지 않는다.

## 11. 구현 경계와 문서 반영

- 계정 모델·서비스·관리자 라우트·사용자 목록: 단계 부여, 행별 권한·활성 상태 변경, 이름 검색, 임시 비밀번호 발급.
- 인증 컨텍스트: 단계 정보 전달, 민감 쓰기 동작의 최신 권한 확인.
- 일정 모델·서비스·별도 라우트·템플릿: 승인 규칙과 이력을 프로젝트 기본 서비스에서 분리.
- 프로젝트 등록·상세·목록과 CSS: 세 날짜 입력·조회·반응형 배치.
- 패키지 서비스: 기존 v2와 두 신규 날짜의 왕복 호환.
- Alembic 및 모델 등록: 새 스키마와 메타데이터 등록.
- 구현 시 `prd.md`, 기능 요구사항서, 관련 배포 지침, `change log.md`에 승인된 후속 고도화 범위를 반영. 오류·외부 제약이 확인되면 `error.md` 갱신.

단계 권한은 일정과 계정 관리에 적용한다. 가격·BOM·견적 등 다른 업무의 새로운 승인 제도를 추가하지 않는다. 고객 납기일·입고 일정·FOB 일정과 ERP 품목별 예정 납기는 별개의 값이다.

## 12. 수용 기준과 검증

1. 마이그레이션 뒤 기존 고객 납기일과 관리자 권한이 보존되고 일반 계정은 1단계다.
2. 가입 승인과 수동 등록에서 단계 선택이 반영되며, 기존 계정 행별 저장은 선택한 계정에만 적용된다. 일반 사용자는 위조 요청으로 단계 변경·계정 복구를 수행할 수 없다.
3. 1단계 요청만으로 프로젝트 일정이 변하지 않는다. 2단계·관리자 승인 후 세 날짜와 이력이 함께 갱신되고 직접 수정도 동작한다.
4. 날짜 지우기, 미입력, 윤년 등 유효 날짜 처리와 잘못된 날짜 오류를 검증한다. 변경이 없는 제출은 기록을 늘리지 않는다.
5. 같은 요청의 재승인·동시 승인·동시 요청 생성이 중복 반영되지 않는다. 일정 변경 후 오래된 화면과 요청이 최신 값을 덮지 못한다. 이 항목은 PostgreSQL에서 실제 트랜잭션으로 확인한다.
6. 계정 강등·비활성화 또는 재발급 직후 이전 세션의 민감 쓰기가 차단된다. 인증 캐시가 남아 있어도 서버 DB 권한 확인이 우선한다.
7. 재발급 비밀번호로 로그인하면 변경 화면을 거쳐야 업무 화면에 접근한다. 이전 비밀번호와 이전 세션은 사용할 수 없으며 비밀번호 평문이 DB·감사 이력에 없다.
8. 이전 v2 가져오기와 새 세 날짜의 패키지 왕복을 확인하고 기존 프로젝트 덮어쓰기 차단을 유지한다.
9. 데스크탑과 모바일에서 단계 표시가 진행 상태 바로 아래에 있고, 세 날짜 선택·저장·요청/처리 결과와 관리자 행별 권한 저장이 읽기 쉽게 동작한다.
10. 기존 로그인·첫 로그인 변경·관리자 가입 승인·프로젝트 등록 동작을 회귀 확인한다. 관련 자동 테스트, 린트·컴파일, DB 마이그레이션 및 배포 결과를 각각 기록한다.
11. 비활성 계정의 로그인과 기존 세션 접근이 차단되고 정확한 만료 문구가 표시된다. 잘못된 비밀번호는 일반 로그인 오류로 처리한다. 재활성화 후 새 로그인은 가능하지만 이전 세션은 되살아나지 않는다. 한 행의 상태 저장으로 다른 계정이나 단계 권한이 바뀌지 않는다.
